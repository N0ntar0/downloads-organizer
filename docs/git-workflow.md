# Git / GitHub運用方針

最終更新: 2026-10-27

この文書は、このリポジトリのGit / GitHub運用の正典です。生駒祭公式サイト（ikomasai/ikomasai-hp）の
運用方針に則り、個人開発・公開リポジトリ向けに調整しています。AIが実行するときの詳細手順は
[AIエージェント向けGit実行規則](./ai/git-operations.md) で管理し、ここでは判断のための方針を説明します。

## まず読む

### 基本思想

> ルールを人間が覚えるのではなく、AIにルールを実行させ、人間は共有・統合・公開の判断を行う。

人間が担当することは次のとおりです。

- 何を開発するか決める
- AIへ作業を指示する
- AIが作った変更と検証結果を確認する
- PushとPull Request作成を、表示される承認画面で承認する
- Pull Requestをレビューし、Mergeする

通常のGit操作、Issue整理、ブランチ名の決定、コミット分割、品質確認、PR本文の準備はAIへ
任せられます。たとえば次のように指示します。

```text
Issue #12 の作業を開始して
```

AIはPushやPull Request作成、Mergeを勝手に行いません。AIは変更内容と検証結果を日本語で報告した
うえで操作を実行し、そこで出る承認画面での承認を、人間の明示的な許可として扱います。

対象はPush、Pull Request作成、作業ブランチの削除の3種です。Pull RequestのMerge、Force Push、
`main` の削除、リポジトリ設定の変更などは、承認画面のワンクリックでは通しません。AIが事前に影響範囲を
説明し、人間が判断してから進めます。

承認画面が出ない環境（非対話実行など）では、AIは報告したところで停止し、会話で明示的な許可を
求めます。判断がつかない場合は停止する方を選びます。

### ikomasai-hp との違い

| 項目 | ikomasai-hp | このリポジトリ |
| --- | --- | --- |
| 恒久ブランチ | `main`（本番）と `develop`（次回公開候補） | `main` だけ |
| 大枠タスクの分岐元・Merge先 | `develop` | `main` |
| 本番への反映 | 管理画面の承認処理が `develop` を `main` へ反映 | `main` へのMergeがそのまま公開 |
| ブランチ保護 | Privateのためローカルhookのみ | ローカルhookとGitHubのRulesets |
| 品質ゲート | `pnpm verify` | `scripts/verify.ps1` |

個人開発で承認つきの公開フローがないため、`develop` は置いていません。`main` は利用者が
`git clone` するブランチなので、未完成の変更を入れないことは ikomasai-hp の `develop` と同じです。

## 詳細

### Issueを起点にする

Issueは仕様の正本です。原則として、コードやドキュメントを変更する前にIssueを作成します。Issueには
最低限、概要、背景・目的、対応予定内容、完了条件を記載します。

まとまった成果を表す「大枠Issue」を作り、次に当てはまる場合は子Issueへの分割を検討します。

- 1ブランチでは変更が大きすぎる
- 独立して実装・レビューできる作業が複数ある
- レビュー単位を分けた方が理解しやすい

子Issueには親Issue番号を明記し、大枠Issue側では子Issueをチェックリストで管理します。

### 仕様検討フェーズ

**Issueを作成したこと自体は実装開始の合図になりません。**内容が十分に整理され、担当者が
「この仕様で実装してよい」と判断できる状態になってから、ブランチ作成と実装へ進みます。

```text
アイデア・要望 → 壁打ち → Issue作成 → 必要に応じて壁打ち → Issue更新 → 仕様確定 → 実装開始
ある程度明確な要望 → Issue作成 → 壁打ち → Issue更新 → 仕様確定 → 実装開始
```

#### 状態ラベル

| ラベル       | 意味                           | 誰が付けるか                               |
| :----------- | :----------------------------- | :----------------------------------------- |
| `仕様検討中` | 壁打ち中。仕様が未確定         | Issue作成時にAIが付ける                    |
| `実装可能`   | 仕様確定済み。実装へ進んでよい | **人間が判断し、その指示でAIが付け替える** |
| `実装中`     | 作業ブランチ作成済み           | ブランチ作成時にAIが付け替える             |

```powershell
gh issue list --label 実装可能
```

#### 壁打ちが不要なタスク

typoの修正や明らかなバグ修正など、依頼の時点で仕様が明確なタスクに長い壁打ちは求めません。
AIが「変更対象が特定済み」「完了条件が一意」「利用者への影響に判断の余地がない」といった根拠を示して
`実装可能` への遷移を提案できます。提案であって決定ではないため、同意はしてください。

### ブランチ構成

```text
main（公開中の状態）
├─ 12-feat/stale-days（大枠タスク）
│  ├─ 13-feat/stale-days-config（子タスク）
│  └─ 14-docs/stale-days-readme（子タスク）
└─ 20-fix/zip-detection（大枠タスク）
```

#### `main`

`main` は公開中の状態を保持する唯一の恒久ブランチです。利用者はここを `git clone` するので、
完成して検証済みのタスクだけを統合します。

直接コミットを防ぐため、clone後に次を実行してリポジトリ同梱のgit hookを有効にします。

```powershell
git config core.hooksPath .githooks
```

`pre-commit` は `main` 上での直接コミットを、`pre-push` は `main` 宛の直接Push・削除をブロックします。
`pre-commit` は、どのブランチでもステージした内容の衝突マーカーを検査します。緊急時に限り
`ALLOW_PROTECTED_COMMIT=1` または `ALLOW_PROTECTED_PUSH=1` で回避できますが、GitHub側の保護は
回避できません。

#### 守れる範囲

公開リポジトリのため、GitHubのRulesets（ルール名「main を保護」）も使えます。

| 経路 | ローカルhook | GitHubのRulesets |
| :--- | :--- | :--- |
| `main` 上での `git commit` | 防げる | ―（ローカル操作） |
| `main` への直接Push | 防げる | 防げる |
| `main` へのforce push | 防げる | 防げる |
| `main` の削除 | 防げる | 防げる |
| `core.hooksPath` 未設定のクローン、`--no-verify` | 防げない | 防げる |
| Pull Requestを経由しない変更 | ― | 防げる（PR必須） |

個人開発のため、Pull Requestのレビュー承認数は0件にしています。

#### 子タスクブランチ

子Issueに対応し、親の大枠タスクブランチから分岐します。`main` から直接作りません。

### ブランチ命名

```text
<Issue番号>-<type>/<内容>
```

| type       | 用途                         |
| ---------- | ---------------------------- |
| `feat`     | 新機能・機能追加             |
| `fix`      | バグ修正                     |
| `refactor` | 挙動を変えないコード改善     |
| `style`    | 見た目・書式の変更           |
| `docs`     | ドキュメント変更             |
| `chore`    | 設定・環境整備・テストなど   |

### Pull Requestのマージ先

```text
13-feat/stale-days-config（子タスク）
        ↓ Pull Request
12-feat/stale-days（大枠タスク）
        ↓ 大枠タスク完成後にPull Request
main
```

### コミット

コミットは変更ファイルのまとまりではなく、後から意図を説明できる変更単位に分けます。

```text
<type>: <変更内容> #<Issue番号>
```

良い例:

```text
feat: 削除候補の保管期間を設定できるようにする #12
fix: 同名フォルダがあるzipを削除候補にできない問題を修正 #20
```

悪い例:

```text
修正
update
```

既存履歴（Issue #1 より前のコミット）は書き換えません。Issueとの関係は、コミット件名の
`#<Issue番号>` とPR本文の `Closes #<Issue番号>` の両方で明示します。

### ReviewとMerge

Mergeは人間が行います。AIはPull Requestの内容と状態を確認できますが、Mergeは行いません。

`main` 宛てのPull Requestなので、本文の `Closes #<番号>` によりMerge時にIssueは自動でクローズされます。
子タスク（親タスクのブランチ宛て）のIssueは自動クローズされないため、Mergeを確認したら手動でクローズします。

### 作業ブランチの整理

作業ブランチは一時的なものとして扱い、Pull RequestのMerge後に削除します。GitHub上には原則として、
`main` と現在作業中のブランチだけが残る状態を維持します。削除前の確認手順は
[AIエージェント向けGit実行規則](./ai/git-operations.md#ブランチ削除前のチェックリスト) にあります。

### 検証はローカルで行う

本リポジトリにCIはありません。**検証の正典はローカル実行**です。Push前に次を実行し、その結果を
Pull Requestへ記録します。変更がドキュメントだけであっても省略しません。

```powershell
.\scripts\verify.ps1
```

### Force Push

Force Push自体は禁止しませんが、`main` へのforce pushはRulesetsで拒否されます。作業ブランチでも、
AIが無断で `git push --force` や `git push --force-with-lease` を実行することは禁止します。

### `main` への統合条件

大枠タスクを `main` へMergeする前に、すべて確認します。

- [ ] 大枠タスクの実装が完了している
- [ ] 必要な子タスクが完了している
- [ ] `scripts/verify.ps1` を通過している
- [ ] 挙動が変わる場合、実際のフォルダで `-DryRun` の結果を確認した
- [ ] README と `rules.example.json` が新しい挙動・設定項目に追従している
- [ ] 明らかな既知の不具合が残っていない
